## 0. Executive Summary & Readiness Verdict

### 0.1 Verdict on the claimed status `PRODUCTION_READY — GREEN (544/1/0)`

**The claimed status is not sustainable as stated. Recommended reclassification: `AMBER — CONDITIONAL` (capture pipeline) / `RED` (rollback subsystem) / `RED` (governance accuracy).**

The test suite is real, sizeable, and largely well-constructed — but it is green against a **different system than the one documented**. The audit found that substantial portions of the "modern" Stage 02/03/05 architecture (`LifecycleController` as lifecycle authority, `ReconcilerDaemon`, `ProjectWriter` single-writer threads, the durable `data/projects/<slug>/` layout, and the non-destructive rollback workflow) exist as **well-tested but unwired code**, while the production runtime is still driven by the legacy `Supervisor` + `StorageRotator` + `SessionDB` stack that Stages 01–03 were chartered to replace. Meanwhile, the governance documents (`CURRENT_STATE.md`, `ARCHITECTURE_CURRENT.md`, `FINAL_AUDIT.md`, `RELEASE_ACCEPTANCE.md`) describe the modern architecture as live and cite evidence (class names, constants, modules) that does not exist in the codebase.

Four defects are severe enough to block the Stage 09 pilot as planned:

| # | Blocker | One-line impact |
| :-: | :--- | :--- |
| **B-1** | `ChangeProcessor` self-deadlock on `needs_reconcile` bundles (`scripts/core/change_processor.py:151,163,250`) | The exact 20,000-file overflow scenario the bounded queue was designed for **permanently hangs the capture pipeline** of a live worker; heartbeat keeps ticking, so no supervisor layer detects it. Untested end-to-end. |
| **B-2** | Production rollback route executes the **destructive legacy path**: `git checkout -f` + bare `git clean -fd` + `reset --hard` + `DELETE FROM events/patches` (`scripts/server/routes_events.py:425` → `scripts/storage/rollback.py:332–455` → `scripts/git/shadow_rollback.py:109–114`) | Directly violates locked ADR-008, INV-16, INV-25. User workspace files created after the status scan can be destroyed; telemetry history is deleted, not superseded. The compliant non-destructive implementation exists but is never invoked (`non_destructive=False` default). |
| **B-3** | The entire rollback capture-pause stack is non-functional: `send_control_command` **does not exist** (all 5 call sites are swallowed `ImportError`s — `scripts/storage/rollback.py:82,92,223,247,326`), the worker's `SEAL` handler calls a nonexistent `flush_pending()` method (`scripts/project_worker.py:154–155`), and `ProjectWatcher` has no `pause()/resume()` | Rollback proceeds while the capture pipeline is still live; pending bursts can commit mid-restore, corrupting ChangeSet↔Git↔SQLite consistency (ADR-019). |
| **B-4** | Sensitive-file content leaks into telemetry: `IgnorePolicy.should_watch()` deliberately admits `.env*`/`*.pem`/`*.key` as "metadata-only", but the per-burst diff path never consults `should_diff()`/`should_stage()` before `compute_diff()`/`record_patch()` (`scripts/core/worker_bundle.py:50–110`, `scripts/storage/ignore_policy.py:297–330`) | Secret **file contents** are persisted in plaintext to `session.db` `patches`, `patches/event_N.patch`, the `baseline/` directory, and rendered in the UI diff viewer. Shadow Git staging is protected only incidentally (hardened `.gitignore` + `check-ignore`). |

In addition, the "30 invariants strictly active and enforced" claim in `CURRENT_STATE.md` does not survive code-level verification: **5 invariants are violated, 15 are degraded, 10 hold** (Section 2.1).

### 0.2 What is genuinely strong (credit where due)

The review is not uniformly negative — several subsystems are well-engineered and match their specs:

- **`BurstAssembler` core loop** (`scripts/core/burst_assembler.py`): the condition-variable dual-deadline algorithm (`due = min(last+quiet, first+max)`) is correctly implemented, monotonic-clock based, notification-driven, and free of the legacy DWORD-timer overflow class. Extraction under lock / enqueue outside lock is the right pattern.
- **NUL-delimited pathspec staging** (`scripts/git/shadow_commit.py:stage_paths_nul`): correctly defeats the Windows 8,191-char `CreateProcess` limit; `git check-ignore -z --stdin` filtering; hardened git env (`GIT_TERMINAL_PROMPT=0`, stripped `GIT_DIR/GIT_WORK_TREE/GIT_INDEX_FILE`); `gc.auto=0`, `core.longpaths`, `core.autocrlf=false`, `core.quotepath=false` are all set per SPEC-004 (but see F-1.16 on gc).
- **Ghost-commit prevention**: `git diff --cached --quiet` gate before commit; no `--allow-empty` in the burst path (INV-14 holds for bursts).
- **Event-before-Git durability ordering** (`scripts/core/worker_bundle.py`): events + patches are committed before `commit_changeset`; git failure preserves the event and records `git_ops` state (INV-13 holds).
- **HTTP security layer** (`scripts/server/security.py`): Host allowlist with IPv6/port parsing, strict Origin validation on mutations, no wildcard CORS, constant-time token compare, 10 MB body cap, JSON content-type enforcement, error-message path/secret scrubbing. The canonical `/events*` GET routes are properly read-only (`mode=ro` + `PRAGMA query_only=ON`, connections closed in `finally`).
- **`time_utils.py`** (ADR-015): single UTC utility, offset-aware legacy parsing, heartbeat-age clamping — solid, with two minor caveats (F-3.6).
- **Fingerprint comparison logic** (`scripts/storage/fingerprint.py`): correct empty-file/deletion/binary/timestamp-only-rewrite semantics (INV-15 holds at the logic level; see F-1.6 for the Windows locked-file edge).
- **Atomic sentinel writes**: `safe_write_status_json` (tmp + `os.replace` + exponential backoff on `WinError 5/32`) and `mark_stale_pid` (collision-safe `.stale.N` suffixing for `WinError 183`) are exactly the right Windows patterns.
- **Schema migration engine** (`scripts/storage/schema_migration.py`): additive `ALTER TABLE`, `PRAGMA user_version` gating, and — importantly — the right indexes, including `idx_events_session_read (session_id, event_type, first_file_touched)` for the READ-dedup query.
- **`compatibility_reader.py`** (ADR-018): genuinely read-only dynamic projection (`('ev_' || id) AS event_id`) with per-column PRAGMA introspection — the cleanest module in the storage layer.
- **Fault-injection harness design** (`scripts/core/faults.py`): deterministic, env-gated, one-shot capable, `os._exit` semantics — good; the gap is coverage breadth (Section 3.2), not design.
- **Worker identity verification** (`validate_worker_process`): real 6-attribute checking (PID, create-time tolerance, exe stem, exact `--worker-id` token, canonical `--path`, `--engine-root`) with Windows case-folding — when it is actually called (see F-2.8 for the paths that skip it).

## 1. Codebase Integrity, Bug Detection & Edge-Case Scan

Scope: `scripts/core/`, `scripts/storage/`, `scripts/controller/`, `scripts/git/` (plus the server/worker call paths they participate in). Findings are prefixed **F-x.y** and mapped to the Section 5 ledger.

### 1.1 Windows OS specifics (file locking, CLI limits, long paths, timestamp races)

**F-1.1 — `TerminateProcess` is the "cooperative" stop on Windows (mis-labeled clean kills).**
`stop_process_cooperatively()` (`scripts/controller/process.py:94–133`) performs "Step 1: Cooperative stop request" via `send_stop_pid(pid)`, which on Windows is `psutil.Process(pid).terminate()` → `TerminateProcess` (`scripts/core/spawner.py:355–372`; the docstring itself concedes this). `TerminateProcess` is an unconditional hard kill: no signal handler runs, `atexit` (`_crash_handler`) does not run, the `ProjectWriter`/`SessionDB` is never drained or checkpointed, pending bursts are lost, and `worker.pid`/`session.lock`/`worker.status.json` sentinels are left on disk. Because `wait_for_pid_exit()` then returns immediately, the function reports `(clean_stop=True, "clean_stop")` — an escalated hard kill is **recorded as a clean stop** (`controller.py:277–300` then transitions to `STOPPED`, not `INTERRUPTED`). The supervisor path (`worker_helpers.stop_worker_process`, stages 3/4) has the same defect in miniature: escalation calls `psutil.terminate()/kill()` guarded only by `pid_exists()` (`worker_helpers.py:306–308, 380–425`) — no create-time/worker-id re-verification at kill time, so a recycled PID can be terminated (ADR-012 requires identity checks before termination). Python's Windows signal model makes this worse: `SIGTERM` handlers never fire (there is no SIGTERM delivery), `SIGBREAK` is unreachable for `DETACHED_PROCESS` workers (no console), so the only *real* graceful channel on Windows is the file/IPC sentinel path — which must therefore never be short-circuited (see F-1.2, F-2.6).

**F-1.2 — Control-file protocol is fragile: non-atomic writes + default-to-STOP on read error + wrong directory for `stop.cmd`.**
- The supervisor writes `worker.control` with a bare `ctrl_file.write_text(...)` (`worker_helpers.py:333–338`) — **not** tmp+replace, unlike every other sentinel in the codebase. The worker heartbeat reads it every 100 ms (`worker_bundle.py:_run_heartbeat`), so a torn/partial read is possible; worse, if the read raises (file vanished between `exists()` and `read_text` — e.g., concurrent delete, AV lock), the handler **defaults to `content = "STOP"` and shuts the worker down**. A transient filesystem error thus becomes a spurious graceful stop.
- The controller's fallback writes `stop.cmd` to `engine_root/locks/stop_<slug>.cmd` (`controller.py:279–284`), but the worker only polls `current/<slug>/stop.cmd` (`worker_bundle.py`). The controller's stop.cmd stage can therefore never be observed by the worker (latent — controller path unwired).
- `worker.control.json` (loopback HTTP channel) is written atomically (`control_channel.py:_write_control_info`), but the constructor's `tmp.replace(info_file)` is unprotected: an AV/indexer holding the target without `FILE_SHARE_DELETE` raises `WinError 5` out of the `WorkerControlServer.__init__`, which `project_worker.main()` catches and downgrades to "Could not start loopback control channel" — the worker then runs **without** its IPC channel, and controller stops silently fall through to F-1.1's kill path.

**F-1.3 — Archive-time directory moves vs open handles (`WinError 32`) are mitigated by `sleep(1.2)`.**
`Supervisor.stop_project` kills/exits the worker, then `time.sleep(1.2)` "to ensure Windows file handles on SQLite WAL files are released" (`supervisor.py:363–365`), deletes sentinels, opens its own `SessionDB` write connection (`supervisor.py:382–395`), and finally calls `rotator.archive_project(slug)` — a physical `current/<slug>` → `last_run/`/`history/` directory move (`rotator.py:143–166`). Sleep-based handle-release synchronization is unsound: `SessionDB._get_ro_conn()` creates **thread-local read-only connections that are only closed for the calling thread** in `close()` (`db.py:_get_ro_conn/close`) — server request threads (daemon, still running per `server_daemon.shutdown()` ordering, F-1.4) and supervisor-internal threads can hold open handles on `session.db` when the rename executes → `WinError 32/5` on `rename`, partial moves, or silent `ignore_errors` data stranding. The `archive_project` liveness refusal check (pid file + `is_process_alive`) is correct but TOCTOU-racy against a concurrent start.

**F-1.4 — Server shutdown ordering strands readers mid-archive.**
`EngineWebServer.shutdown()` (`server_daemon.py:160–186`) sets the shutdown event, stops the AI executor, calls `ThreadingHTTPServer.shutdown()/server_close()` (which does **not** join per-request daemon threads), then immediately `supervisor.shutdown()` → `stop_all()` → archives/moves project directories. In-flight GET handlers (SSE threads wake within 10 s; DB reads may be mid-query) can still hold `mode=ro` handles on the very files being moved → the F-1.3 failure class, triggered by ordinary Ctrl+C.

**F-1.5 — CLI/argument-length exposure remains in the rollback restore path.**
Burst staging correctly uses `--pathspec-from-file=- --pathspec-file-nul` (SPEC-004). But `restore_files_non_destructive()` checks out in batches of **50 raw pathspec arguments** (`shadow_rollback.py:255–275`), and `rollback_to_burst()` runs `checkout -f <hash> -- .` — with deeply nested/Unicode workspace paths, 50 × ~200-char paths approach/exceed the 8,191-char `CreateProcessW` limit; failure is logged as a warning and the function **still returns `True`** (success), so a partially restored workspace is reported as fully restored. The WMI spawn fallback (`spawner.py:270–300`) also embeds the whole command line base64-encoded inside a PowerShell `-EncodedCommand` payload — a second, nested argument-length surface for pathological path lengths.

**F-1.6 — NTFS sharing-mode traps converted into phantom telemetry.**
`compute_fingerprint()` treats any `OSError` on `stat()`/`open()` as `exists=False` (`fingerprint.py:75–130`), and `is_binary_file()` returns `True` on `OSError` (`diff_calc.py:78–90`). On Windows, files held with deny-read sharing (Outlook PSTs, some installers, AV quarantine scans, `sqlite3` files of other tools) raise `PermissionError` — the engine will therefore record a **phantom "deleted" effective change** (manifest deletion + potential shadow-git delete staging when the lock clears and the file "returns" as "created"). Similarly, the create-time tolerance is inconsistent between layers: 0.5 s in `is_process_alive()` (`process.py:47–52`) vs 3.0 s in `validate_worker_process`/`_WorkerEntry.is_alive` — the same worker can be "alive" to one verifier and "recycled" to another within the same second (NTFS/`psutil` create-time resolution is fine; the inconsistency is the defect).

**F-1.7 — Long-path posture is half-done.**
Shadow git sets `core.longpaths=true`, but Python-side I/O (`open()`, `os.walk`, `Path.resolve()`) does not use `\\?\` prefixes and depends on the Win10+ long-path OS policy being enabled; `watchdog`'s `ReadDirectoryChangesW` buffer (default) can also silently miss events during deep-tree bulk operations. No preflight check verifies the `LongPathsEnabled` registry policy even though preflight already checks Python version, WAL, and tiers (`preflight.py:52–120`).

**F-1.8 — Legacy `STILL_ACTIVE == 259` false positive.** The no-psutil Windows fallback in `is_process_alive()` treats exit code 259 as alive (`process.py:60–75`); a process that legitimately exits with 259 is immortal to the fallback. psutil is a hard dependency in practice, so this is defense-in-depth only — but the fallback exists precisely for the "psutil missing" case where correctness matters most.

### 1.2 Concurrency & deadlocks (ProjectWriter, BurstAssembler, LifecycleController, and the live legacy path)

**F-2.1 — P0 DEADLOCK: `ChangeProcessor` re-acquires its own non-reentrant lock on the overflow-recovery path.**
`_processing_lock = threading.Lock()` (`change_processor.py:67`). The consumer loop processes bundles **under** that lock (`change_processor.py:150–152`), and `_process_single_bundle` begins with:
```python
if bundle.get("needs_reconcile"):
    self.reconcile(reason="queue_overflow")     # change_processor.py:161–163
```
`reconcile()` itself does `with self._processing_lock:` (`change_processor.py:250`). A `threading.Lock` is not reentrant → the ChangeProcessor thread **self-deadlocks while holding the lock**, on precisely the bundle produced by a 20,000-path overflow (`burst_assembler.py:add()` sets `needs_reconcile=True`). Consequences: bursts stop being processed forever; the downstream queue (maxsize 1000) fills; `BurstAssembler._enqueue_downstream` then drops whole bundles after 5 s each (F-4.2); the worker's heartbeat thread keeps publishing fresh status, so `Supervisor.get_status`, the reconciler, and `/health` all report a healthy ACTIVE worker — a **zombie capture state invisible to every supervision layer**. `drain()` (`change_processor.py:112`) has the identical nesting, so graceful shutdown of such a worker also hangs (until join timeouts). The unit test `test_queue_overflow_recovered` (`tests/test_fault_injection_and_invariants.py:313–327`) stops at the assembler flags and never feeds an overflow bundle to a `ChangeProcessor` — which is why 544 green tests missed this.
*Fix:* make `_processing_lock` an `RLock`, or (better) hoist the reconcile decision out of `_process_single_bundle` into the loop *before* lock acquisition, and add the missing end-to-end regression test.

**F-2.2 — Nested `ProjectOperationLock` self-conflict in `resume_project`/`delete_project` (latent, controller path).**
`resume_project` acquires `ProjectOperationLock(engine_root, project_id)` and then calls `self.start_project(...)`, which constructs a **second** `ProjectOperationLock` instance on the same path (`controller.py:319–333, 349–366, 129–133`). The in-process registry RLock is shared per canonical path (`locks.py:47–63`) so the thread-lock stage succeeds reentrantly — but the OS file-lock stage opens a **new fd** and attempts `msvcrt.locking(..., LK_NBLCK, 1)` (Windows) / `flock(LOCK_EX|LOCK_NB)` (POSIX) on a region the same process already locks via a *different* file description. Both OSes reject same-process double-locks across independent handles/fds → the inner acquire polls for the full 10 s timeout and raises `OperationLockConflictError`. So `resume_project` can never succeed in-process, and `delete_project`'s inner `stop_project` stalls 10 s, fails, and is swallowed by `except Exception: pass` (`controller.py:360–363`) before deleting the registry rows — **guaranteeing an orphaned, still-running worker with no registry entry**. `FileLock` implements its own reentrancy accounting (`_owner_thread`/`_reentrant_count`), which would have handled this if the same instance were reused; the bug is instance-per-call. No test exercises `controller.resume_project`/`delete_project` against the real lock (tests inject mock spawners and call routes that bypass the controller).

**F-2.3 — Cross-thread transaction interleaving via raw `SessionDB.conn` bypasses (live production path).**
`SessionDB` serializes its own API through an RLock with explicit `BEGIN IMMEDIATE` transactions (`db.py:transaction/_execute`). But three production call sites use the **raw connection** without the lock:
- `record_git_op_state()` / `update_git_op_state()` — `conn.cursor().execute(...)` + `conn.commit()` (`shadow_commit.py:415–455`), called from the ChangeProcessor thread inside `_handle_event_bundle`;
- the commit-attribution `UPDATE events SET commit_hash = ..., git_state = ...` (`worker_bundle.py:166–172`), same thread;
- `supervisor.stop_project` and `rollback_burst`/`execute_non_destructive_rollback` opening *separate writable connections from other processes* (`supervisor.py:382`, `rollback.py:105, 244, 395`).
With `isolation_level=None`, a raw statement executed while another thread's explicit `BEGIN IMMEDIATE` transaction is open **joins that transaction**; the raw `conn.commit()` then commits the *other thread's* partial work, and its subsequent `COMMIT` raises "no transaction is active" → its `transaction()` handler rolls back → the concurrent `record_event` (e.g., a READ event from the ProcessInspector thread) fails or disappears. This is a live race in the shipping configuration (bursts processing while READ/EXEC telemetry flows), violating INV-12 in spirit and producing nondeterministic single-row losses that no integrity check will ever see.

**F-2.4 — `ProjectWriter` shutdown races (latent — component unwired).**
(a) `submit_critical(..., timeout=None)` blocks forever on `put(block=True, timeout=None)` (`writer.py:110–140`); the stop guard requires **both** `_is_stopping` and `_stop_event` — a submitter that passes the guard between the two flags while the writer loop has exited and the queue is full hangs permanently. (b) `stop()` proceeds to `PRAGMA wal_checkpoint(TRUNCATE)` + `conn.close()` on the shared connection **after a join timeout** (`writer.py:340–360`) — i.e., possibly while the writer thread is still mid-batch on the same `check_same_thread=False` connection → `ProgrammingError`/corruption window. (c) `drain()` spins on `queue.empty()` then `queue.join()` — an operation dequeued but not yet `task_done()`d keeps `join()` waiting past the timeout with no escape. None of this ships today (F-5.1), but it must be fixed **before** the writer is wired per the ADR-020 decision.

**F-2.5 — Reconciler vs `start_project`: the STARTING window has no worker record (latent, controller path).**
`start_project` transitions the project to `STARTING` (`controller.py:169`) and only records the worker **after** the spawn handshake returns (`controller.py:197`) — a window of up to `_BOOT_TIMEOUT_S = 8 s`. `Reconciler._reconcile_known_projects` inspects `STARTING` projects, but the startup-grace protection is keyed on `active_worker.started_at` (`reconciler.py:102–110`) — with **no worker row**, grace is skipped and the else-branch marks the project `INTERRUPTED` ("worker process is gone (PID None)"). The in-flight start then fails its `STARTING→INDEXING` transition with `InvalidStateTransitionError` while the spawned worker runs on, unregistered — orphaned. Fix: insert the worker row (pid NULL, state STARTING) *before* spawn, and/or apply grace based on the project's `updated_at`/operation record.

**F-2.6 — PAUSE/SEAL/RESUME are a fiction end-to-end (live rollback path).**
Triple failure, independently sufficient:
1. `rollback.py` imports `send_control_command` from `controller.control_channel` — the module only defines `send_worker_command` (different name **and** signature). All five call sites (`rollback.py:82, 92, 223, 247, 326`) raise `ImportError` inside `try/except Exception: pass` → PAUSE/SEAL/RESUME never happen, silently.
2. Even with a working transport, the worker's `SEAL` handler calls `worker_state.event_bundler.flush_pending()` guarded by `hasattr` — `BurstAssembler` exposes `flush_now`/`flush_burst_now`/`flush`, **not** `flush_pending` → no-op with an "ok" response (`project_worker.py:152–156`). `RELOAD_CONFIG` and `SUPPRESS` likewise return success without doing anything.
3. `PAUSE` calls `project_watcher.pause()` guarded by `hasattr` — `ProjectWatcher` has no `pause()` (`watcher_fs.py`); the only real pause mechanism is the `.engine_sync.lock` file checked per-event by the watchdog handler (`watcher_fs.py:_is_sync_locked`), which suppresses **new** events but does nothing about events already pending in `BurstAssembler` — those seal on their quiet deadline and are committed by `ChangeProcessor` **during** the restore, mid-`git checkout` of the same files.
Net effect: SPEC-004's rollback sequence (PAUSE → SEAL → snapshot → plan → restore) executes as (write lock file → snapshot → plan → restore **against a live pipeline**).

**F-2.7 — No cross-process mutual exclusion on the live lifecycle path.**
`ProjectOperationLock`/`EngineLock` guard only `LifecycleController` operations — which production never uses (F-5.1). The live path (`Supervisor.start_project/stop_project`, invoked from `start.py` CLI **and** HTTP routes) has **no inter-process lock**: two engine processes (CLI while UI runs; or a second `start.py ui` silently binding port 8766 via the 10-port fallback in `server_daemon.start()`) can concurrently start/stop/archive the same `current/<slug>` directory — the original "two-Supervisor split-brain" defect class, resurrected at the process boundary. `EngineLock` *is* acquired every 5 s by the reaper-delegated reconcile pass and by `register_project`, but start/stop never take it.

**F-2.8 — Lock-ordering audit (no classic ABBA cycles found).**
Orderings observed: op-lock → registry-RLock (controller), engine-lock → registry-RLock (reconciler), SessionDB-RLock (workers), ShadowGit-RLock (workers), `_processing_lock` (ChangeProcessor). No path acquires these in conflicting orders; the deadlock risk in this codebase is **reentrancy** (F-2.1, F-2.2), not lock-order inversion. The reaper's `ctrl.reconcile()` → `EngineLock` can contend with a route-triggered reconcile; the loser raises `OperationLockConflictError`, which the reaper logs at **debug** level and drops (`reaper.py:96–97`) — reconciliation passes can be silently skipped for as long as contention persists.

### 1.3 Resource & memory leaks (queues, sweeps, sockets, buffers)

**F-3.1 — Unbounded in-memory text cache + full disk baseline duplicate of the workspace.**
`wire_worker` constructs a `DiffCalculator` and runs `capture_baseline(target_path)` (`worker_lifecycle.py`, `diff_calc.py:238–300`): every non-binary file's **full content** is read into `self._cache: dict[str,str]` *and* copied to `current/<slug>/baseline/` on disk; `_handle_event_bundle` then re-reads and re-writes full file contents per burst and grows `_cache` monotonically (entries are only ever replaced, never evicted, except on deletion). This contradicts ADR-006 ("eliminates heavy in-memory text caches and baseline directories") and means worker RSS + disk scale with **workspace size × 2**, not with change volume. It is also the single biggest threat to the 09.1 soak (a 2-hour session touching large files ratchets RAM upward with no release) and to the 09.3 storage budget (baseline/ is a third full copy of diffs after session.db `patches` and `patches/*.patch` files — a fourth if you count shadow-git objects).

**F-3.2 — Whole sealed bundles are dropped when the downstream queue saturates — with no accounting.**
`_enqueue_downstream` blocks 5 s on a full `downstream_queue` (default `maxsize=1000`), then logs `error` and **discards the entire bundle** (`burst_assembler.py:348–358`): `drop_counter` is not incremented, `needs_reconcile` (which lived inside the bundle) evaporates, no SSE/health signal is raised. Under sustained bulk activity + slow git commits (2,000-file burst ≈ 2.65 s per `RELEASE_ACCEPTANCE.md` §3.1), queue saturation is reachable — telemetry loss is then silent except in worker.log. `stop()`'s join(5 s)+`flush_now()` sequence can also deliver the final bundle *out of order* when the loop thread is still blocked in its own 5 s enqueue (two threads racing on the same queue).

**F-3.3 — O(events-in-10s) churn scan under the global assembler lock, per event.**
`add()` calls `_prune_and_check_churn(now)` (`burst_assembler.py:192`) which rebuilds a counts dict over the entire `_touch_history` deque **on every single event, under `_cond`** — and discards the return value (the churn answer is only needed by `has_ide_churn()`/`get_debounce_status()`). During an event storm (bulk checkout: 10k+ events/s) this is O(n) per add with n bounded only by the 10-second window → measurable CPU amplification and lock-hold time on the hottest capture path, starving `get_debounce_status()` consumers (heartbeat/status writes take the same lock). `_touch_history` itself is unbounded except by the 10 s prune — under a 50k-events/s storm that is ~500k tuples resident.

**F-3.4 — Per-call object/connection churn in the registry and reaper.**
`EngineRegistry` opens and closes a **new SQLite connection for every method call** (`registry.py:_get_connection` — ~20 methods), each re-issuing four PRAGMAs. The deprecated `ReaperDaemon.reap_dead_workers()` — which *is* the live 5-second daemon in UI mode (`start.py:613–614`) — constructs a **fresh `LifecycleController`** each pass unless `rotator.controller` happens to exist (`reaper.py:84–95`): each construction runs `EngineRegistry._init_db()` (`executescript` DDL + `init_controller_tables`) against `engine.db`, allocates an `EngineLock`, a `Reconciler`, etc. This is per-5s DDL churn against engine.db from a daemon thread, plus repeated file-lock acquisitions; failures are logged at debug only.

**F-3.5 — Small unbounded maps (long-run server process).**
- `SSEManager._coalesce_timestamps` grows one entry per `seal_<project>`/`status_<project>`/`job_<job_id>` key forever (`sse_stream.py:145–150`) — thousands of AI jobs → thousands of dead entries.
- `_InProcessLockRegistry._locks` never prunes (`locks.py:47–63`) — bounded by distinct lock paths, so small, but immortal.
- `Server._batch_jobs` (`server_daemon.py`) accumulates batch job records; pruning not observed in the audited paths.
- Thread-local `ro_conn`s in `SessionDB` are closed only for the thread calling `close()` (F-1.3) — every server request thread that touches a legacy read leaks one open SQLite handle until thread death (daemon threads die only at process exit).

**F-3.6 — Socket/handle lifecycles are otherwise sound.** SSE: ≤25 clients × one daemon thread each, `unregister_client` in `finally`, bounded 50-event queues with drop-oldest, 10 s heartbeat pings that surface dead sockets (`request_handler.py:230–290`) — no leak found. `_QuietThreadingHTTPServer.handle_error` swallowing `ConnectionReset/Aborted/BrokenPipe` is correct for tab-reload churn. The `WorkerControlServer` binds an ephemeral loopback port and `stop()`s (shutdown + server_close + control-file removal) in `main()`'s `finally` — correct; note `shutdown()` must never be called from a handler thread (it isn't, in the current wiring).

**F-3.7 — Process sweeps are bounded but broad.** `sweep_project_processes` iterates `psutil.process_iter` with exact-token matching (good), but matches on **any one** of worker_id / slug / target-path (OR logic, `process_sweeper.py:78–105`), never checks `--engine-root`, and is invoked with `engine_root=None` from `Supervisor.start_project` and from the interlock — so a same-slug worker belonging to a *different engine installation* on the machine is terminated as collateral (ADR-012 requires the canonical engine/target attributes together, not singly).

### 3.2 Fault-injection robustness (the "12 crash scenarios")

The harness (`scripts/core/faults.py`) exposes 12 in-code points: `after_pid_write, during_starting, during_indexing, during_pending_burst, inside_db_transaction (×2), after_event_durability, before_git_commit, during_git_commit, after_git_commit, during_rollback (×2), during_shutdown, during_migration`. Verified recovery-style coverage:

- `test_fault_injection_and_invariants.py`: framework semantics (4 tests) + **one** real-process crash (`after_pid_write`, exit 77) + invariant units.
- `test_v22_stress_faults.py`: three campaigns with real recovery assertions (`integrity_check=ok`, `git fsck` clean, prior-event durability): queue-handoff fault, `inside_db_transaction` during patch recording, `during_git_commit` with `git_ops` replay to `committed`.
- FINAL_AUDIT §7 lists all 12 points as "verified" — but the list is the **harness inventory**, not 12 executed crash-recovery tests. At most ~5 points have dedicated recovery assertions in the two files above; the remainder (notably `during_indexing`, `during_migration`, `during_shutdown`, `during_rollback`, `after_git_commit`) are exercised — if at all — as in-process raises without restart-recovery verification.

**Unverified crash windows (the question asked):**
1. **During active Shadow Git index updates** — confirmed gap: there is *no fault point between `git add` (staging) and `commit`*; a crash after staging leaves a dirty shadow index; recovery relies on `git_ops` replay re-staging, which is only tested for the `during_git_commit` point. No test leaves a stale `index.lock` and verifies the SPEC-004 §5 "lock older than 60 s → unlink" behavior — **because that behavior is not implemented** (F-1.16 ledger row / P2-16): only boot-time preflight cleans `*.lock` under `current/`, so a mid-session git crash fails *every subsequent burst* until engine restart.
2. Between `record_event` and `record_patch` (event persisted, patches missing → ADR-019 divergence) — no fault point, no test.
3. During `wal_checkpoint(TRUNCATE)` at writer/SessionDB close.
4. During `archive_project`'s directory move (the highest-risk Windows filesystem operation in the system).
5. During `capture_baseline` / initial ingestion of a large workspace.
6. During `.worker_secret`/`worker.control.json` bootstrap (worker runs without IPC — F-1.2).
7. Cross-process double-launch (two engines, same root) — no test at all (F-2.7).

### 3.3 Soak & stress sufficiency (v22 2,000-file test; v23 pilot consistency)

- `test_v22`'s 2,000-file stress is **single-shot**: create → one burst → commit → assert `git_latency < 15 s`, `db_latency < 2 s`, DOM window ≤ 35. It proves the pathspec mechanism survives one large burst; it does not prove *long-run durability* — no repetition, no interleaved small bursts, no memory-growth assertions, no watchdog involvement (changes are synthesized directly into a ChangeSet), no AV/locking interference, no WAL-size checkpoints over time. Measured 2.65 s per 2,000-file commit implies a sustained large-burst workload can saturate the 1,000-slot downstream queue within ~7 minutes of continuous activity — precisely the F-3.2 bundle-drop regime, untested.
- The retention test derives **546.3 bytes/event** from a 5,000-event synthetic batch and projects 90-day sizes — but measures **only `session.db` (+WAL)**. It excludes the dominant growth terms: shadow-git loose objects (full file snapshots per burst, `gc.auto=0`, **no gc/maintenance anywhere in the codebase**), the `baseline/` disk duplicate (F-3.1), `patches/*.patch` files, `worker.log` rotation residue across tiers, `trash/`, and history-tier copies after consolidation (consolidated data exists in *both* `history/run_*` DBs and the cumulative `current` DB). Real disk growth is a multiple of the projection; 09.3 planning on 546 B/event alone will under-provision badly (Section 4.4).
- `test_v23` proves per-burst five-layer consistency beautifully at unit scale, but drives components directly (`_execute_burst` helper), so the **live wiring chain** (watchdog → coalescer(Timer) → IgnorePolicy → BurstAssembler → ChangeProcessor → SessionDB/DiffCalc/ShadowGit) is never integration-tested end-to-end with real filesystem events. That is why wiring-level defects (F-2.6 SEAL no-op, F-4.4 sensitive-file diffing, F-2.1 deadlock) pass a green suite.
- `test_burst_assembler_and_processor` covers ordering/drain semantics of the two components **individually**; the overflow bundle → `reconcile()` interaction (B-1) falls between them.

### 3.4 Highest-value missing tests (ordered)

1. Overflow bundle → ChangeProcessor end-to-end (would have caught B-1 immediately).
2. Rollback route end-to-end on a live-capturing worker: assert non-destructive path taken, PAUSE/SEAL actually observed by worker, events marked `rolled_back` (not deleted), workspace files created mid-rollback survive (would have caught B-2/B-3).
3. Sensitive-file lifecycle: modify `.env` in a workspace **without** `.gitignore`; assert patch text, baseline dir, DB `patches`, and AI payload contain no file content (would have caught B-4).
4. Wiring contract tests: assert `start.py ui` starts `ReconcilerDaemon`; assert worker persistence component is the documented one; assert one canonical `engine.db` path (pins the ADR-020 decision, prevents re-drift).
5. Multi-process lifecycle: two engine processes issuing start/stop/status against one root (F-2.7).
6. Crash-window matrix: one restart-recovery test per each of the 12 fault points, with `integrity_check` + `git fsck` + event-durability assertions (turns FINAL_AUDIT §7's list into fact).
7. Windows stop semantics: assert a stopped-but-unresponsive worker ends `INTERRUPTED` (never `STOPPED`) and that no path labels `TerminateProcess` as clean (F-1.1).
8. Soak harness: 60–120 min loop of scripted edit bursts + bulk ops with RSS/thread-count/handle-count/queue-depth sampling and fail-on-growth thresholds (precursor to 09.1).

### 4.1 First, a governance defect: there are two different "Stage 09"s

These are mutually exclusive plans sharing a number. The roadmap file also still describes itself as the "9-stage master roadmap (Stage 00 through Stage 08)" in `00_START_HERE.md`. **Remediation:** promote the operational items (soak/benchmark/retention) to *Stage 09 — Production Operations Hardening* and renumber the feature-expansion list to *Stage 10 — Future Scope*, updating both documents in one commit. Everything below evaluates the CURRENT_STATE version (the tasked one), with notes on the roadmap version.

### 4.2 09.1 — Real-world 2-hour developer soak

**Assessment: necessary, correctly motivated, but not executable today and under-specified.**

- *Blocking prerequisites:* B-1 (a single `npm install`, branch switch, or `venv` rebuild in a large repo can overflow the assembler and deadlock the worker mid-soak — the soak would "fail" without producing a diagnosable signal, since the zombie state looks healthy); B-4 (soaking against a real repo with `.env` files writes secrets into telemetry for the duration); F-3.1 (2 hours of touching large files ratchets `DiffCalculator._cache` RAM with no eviction — the soak's own "memory stability" criterion would likely trip for the *wrong* reason unless the cache is fixed or bounded first).
- *Missing operational requirements:* (a) explicit pass/fail thresholds — the plan names CPU < 0.5 % idle but nothing for RSS drift (suggest: < +10 % over hours 1–2 after warmup), dropped bundles (must be 0; requires exposing F-3.2 drops as a counter first), `WinError 32/5` occurrences in worker.log (0), heartbeat staleness episodes (0 > 15 s), needs_reconcile events (each must demonstrably recover); (b) an observation harness — periodic scrape of `/api/engine/health` + `worker.status.json` into a CSV with timestamps (the data is already exposed; nobody collects it); (c) scenario script — not just "develop normally": include one bulk operation (>20k paths), one sleep/wake cycle (exercises `ChangeProcessor` wall-vs-monotonic reconcile), one IDE restart, one rollback dry-run + real rollback, one `.gitignore` edit (v23 scenario in vivo), one laptop-on-battery/eco-profile switch; (d) duration — **2 hours is a smoke-soak**; thread/handle/DB-size drifts manifest over days. Recommend 2 h instrumented dry-run → 8 h × 3 consecutive days (one day deliberately heavy) before sign-off; (e) `faulthandler` + `PYTHONFAULTHANDLER=1` in worker env and Windows Error Reporting local dumps enabled so a hang (B-1 class) produces a stack, not a mystery.
- *Sequencing:* fix P0s → re-green suite with §3.4 tests 1–4 → instrument → dry-run → full soak. Timeline: 1.5–2 weeks from fix start.

### 4.3 09.2 — Latency & CPU benchmarking before IPC evaluation

**Assessment: correct discipline (ADR-003's "measure before rewriting" is the right instinct), wrong current evidence base, and pointed at the wrong IPC.**

- The existing `bench/results.json` is `mode: "smoke"`: in-memory ingest (572,606 events/s is a dict-insert benchmark, not a pipeline), one 200-file burst, 10 SSE clients, idle CPU 0.0 % (sampling granularity too coarse to certify < 0.5 %). It cannot support any IPC decision.
- *Measure the hot paths that actually exist:* end-to-end FS-event→`burst_sealed` SSE latency (p50/p95/p99) via real file writes; per-burst git commit time at 10/100/1k/2k/10k files; `process_iter` scan cost vs system process count (two independent scanners run: `ProcessInspector` ~2 s adaptive and `ExecutionTracker` 1.2 s idle / 0.18 s fast — measure their combined idle duty cycle; that, not HTTP, is the likely < 0.5 % CPU budget consumer); status-write amplification (`_write_status_file` fires on *every READ event* plus 2 s heartbeat — each write takes the assembler lock via `get_debounce_status`, contending with capture, F-3.3); SQLite read latency under concurrent write load; `read_project_meta` git-subprocess storms on status polls (F-3.x/INV-3 row — fix or measure, currently up to 2 subprocess spawns × 3 s timeout per status row).
- *The IPC question is mis-framed:* worker↔engine control is **not** primarily loopback HTTP today — it is file-based polling (`worker.control`, `stop.cmd`, `seal_burst.cmd`, `worker.pid`, `worker.status.json` at 10 Hz per worker) plus an *optional* loopback HTTP channel that the controller path never reaches in production. Before evaluating named pipes/gRPC/etc., the benchmark should compare (a) file-polling latency & I/O cost, (b) the existing `WorkerControlServer` HTTP channel (already built, authenticated, idempotent — just unused by the live supervisor path), (c) status quo. My prediction: wiring the *existing* control channel into `Supervisor.stop_project` (replacing F-1.1's kill-first ladder) captures ~all of the benefit at ~zero architectural cost; a new IPC mechanism is not warranted until the numbers say otherwise — which is exactly ADR-003's standard.
- *Timeline:* 1 week to build the benchmark harness (extend `bench/bench_engine.py`), 1 week to collect on target hardware (Windows 10 and 11, AV on — AV interference is a first-class variable on Windows).

### 4.4 09.3 — Retention & auto-vacuuming policy

**Assessment: right initiative, empirically under-scoped; the 546.3 B/event figure is real but measures the smallest of at least six growth terms.**

Missing from the policy scope, in likely order of disk dominance:
1. **`shadow_git/` loose objects** — every burst commits full contents of changed files; `gc.auto=0` (deliberately, to avoid write-time stalls) and **no scheduled `git gc`/`repack` exists anywhere**. A 90-day heavy project will carry tens of thousands of loose objects: slow `git add`/`diff-tree` (O(objects) directory scans on Windows), inflated disk (no delta compression), and eventual `index.lock`-timeout failures. *Policy:* controller-scheduled maintenance window (e.g., nightly or every N bursts when idle: `git repack -ad --window=… --depth=…` + `git prune --expire=<retention>`), with the retention horizon tied to the rollback-anchor requirement (never prune commits reachable from `git_milestones`/`rollbacks` anchors — this is a real constraint that makes naive `gc --prune=90.days` unsafe; document anchor protection before automating).
2. **`baseline/` directories** — a full text duplicate of every workspace (F-3.1). *Policy:* eliminate by completing the ADR-006 migration (manifest fingerprints + shadow-git `show <commit>:<path>` for old content) — this is a P1 fix, not a retention knob; until then, cap baseline to files touched in the current session.
3. **`patches/*.patch` files + `patches` table + shadow-git diffs** — the same diff stored **three times**. *Policy:* pick one canonical store (the DB `patches` table) and make the .patch file export-on-demand; or keep files and NULL the DB column for large diffs.
4. **History-tier duplication** — `consolidate_project_history` copies rows from `history/run_*` and `last_run` into the cumulative `current` DB but never removes the sources → cumulative duplication grows per run. *Policy:* after verified consolidation (row counts + checksums), move source DBs to a compressed archive or trash with TTL.
5. **`session.db` itself** — the 546 B/event term. Note: `PRAGMA auto_vacuum` cannot be changed on an existing database without a `VACUUM INTO` rebuild; the policy needs either (a) `auto_vacuum=INCREMENTAL` set at creation (schema_migration change) + periodic `PRAGMA incremental_vacuum(N)` from the controller, plus (b) a monthly `VACUUM INTO` rotate-and-swap for existing DBs (the rotator already has the move machinery — reuse it under an operation lock, not at stop-time).
6. **`trash/`, `worker.log` × tiers, `engine.db` jobs/analyses** — TTL purges (trash: 30 days default; logs already rotate 5 MB × 3 but accumulate per archived run; jobs: terminal-state pruning after 90 days).
- *Also required:* expose per-artifact disk usage in `/api/engine/health` (session.db, wal, shadow_git, baseline, patches, trash, logs) so retention policy is empirically driven per project — the current projection test cannot see any of this.
- *Timeline:* measurement hooks 0.5 week; policy implementation 2 weeks; then a 30-day accelerated-aging test (scripted 1,000 events/day × 30 with weekly maintenance runs) to validate the bounds before declaring the retention SLO.
